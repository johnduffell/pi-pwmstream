# Development container

This sets up a ready-made Linux environment (Debian 13, arm64) for working on the driver, so you can
build the kernel module and run `make check-all` without installing anything on your own machine and
without a Pi. It also isolates your environment from accessing anything other than supplied secrets
and data, meaning that LLMs such as copilot, compromised libraries, and unreviewed code in this repo
can't exfiltrate any of your unrelated secrets.

Any other Debian 13 arm64 machine works just as well; the packages it needs are listed in the
[development guide](../docs/development.md#hardware-free-checks).

The configuration is generated by Guardian's [devenv](https://github.com/guardian/devenv) from
[`devenv.yaml`](devenv.yaml) and [`escapehatch.json`](escapehatch.json). Edit those, not the
generated `shared/devcontainer.json`.

## Quick start

1. Install Docker and an IDE with devcontainer support (VS Code, IntelliJ and others).
2. Open the repository root in the IDE and then `.devcontainer/shared/devcontainer.json` before
   right clicking and creating the container from it.
3. Wait for creation to finish. The first run installs the build tools and downloads the pinned
   Raspberry Pi kernel headers (SHA-256 verified).
4. In the container's terminal:

```sh
make check-all
```

If creation reported `[setup] Errored!`, see `/var/log/post-create.log`. To repeat the header step
by hand: `sh dev-tools/fetch-kernel-headers.sh --install && make check-kbuild`.

Notes:

- The container needs network access and `sudo` on creation. It is not privileged and mounts no
  hardware or Docker socket; only the project folder is shared with the host.
- Binaries built on a Mac are the wrong format for Linux. Run `make clean` before building in the
  container.
- The Docker container name is fixed as `pi-pwmstream`, so only one can exist at a time. Remove the
  old one before recreating it.
- `user/devcontainer.json` (git-ignored) is an optional variant that merges your personal devenv
  preferences, which can add mounts or dotfiles. Review it before use.

## Changing the configuration

The devenv version is pinned in [`../.tool-versions`](../.tool-versions). After editing
`devenv.yaml`:

```sh
devenv generate
devenv check
```

If `devenv` isn't found (for example in a non-interactive shell), prefix the commands with
`mise exec --`.

## Reaching a Raspberry Pi from the container

Only needed for Pi tests ([`docs/development.md`](../docs/development.md#testing-on-a-pi)).

1. Create a dedicated key in the container and authorise it on the Pi. Don't copy your personal keys
   into the container.

   ```sh
   ssh-keygen -t ed25519 -f ~/.ssh/pi_pwmstream -C pi-pwmstream
   ssh-copy-id -i ~/.ssh/pi_pwmstream.pub user@raspberrypi
   ```

   (Or add the `.pub` file to the Pi's `~/.ssh/authorized_keys` from another machine.)

2. Add to `~/.ssh/config`:

   ```sshconfig
   Host raspberrypi
       User user
       IdentityFile ~/.ssh/pi_pwmstream
       IdentitiesOnly yes
   ```

3. Connect once with `ssh user@raspberrypi` and check the host-key fingerprint against the Pi's own
   before accepting it. Never disable host-key checking. If the container can't resolve
   `raspberrypi`, use the Pi's IP address in the config and the `--host` option.

The key and config live only in the container: recreating it means repeating these steps. Never
commit private keys.

Then, from the repository root (this changes the Pi and emits test waveforms, so it never runs
automatically):

```sh
bash dev-tools/deploy.sh --host user@raspberrypi --install-reload --test
```
